# Length fix (why AI lessons were ~1 minute)
**Cause:** video length = narration length. The mock/demo path writes a fixed 7-scene template (~100 words ≈ 58 s), and for real LLMs nothing enforced the requested duration (the 5-12 min QC check was advisory).
- ✔ `services/lengthplan.py`: word budget from requested minutes (`WPS = 2.45`, calibrated on the real 6m27s render: estimator says 398 s vs 387 s actual, +3%), per-section budgets, `length_check`.
- ✔ Storyboards from a real LLM are built **section by section** (`ai/prompts/storyboard_section.md`; 8 sections with budgets for hook/objectives/concepts/demo/defense/mistakes+real-world/quiz/summary). A section outside ±12% of its budget is re-asked with explicit feedback (max 2 corrections). The stitched storyboard must land within ±20% of the total budget or generation fails and nothing is saved. The script prompt now carries `NARRATION_WORD_TARGET` so scripts have enough depth.
- ✔ QC `duration_matches_request` is **blocking**: duration must be within ±20% of the requested minutes and inside the hard 5-12 min limits. Exempt only for `mock`-generated content (marked "not enforced"); manual/imported and API-generated lessons are enforced.
- ✔ `POST /api/lessons/{id}/storyboard/regenerate` rebuilds the storyboard to fit and sends the lesson back to SCRIPT_APPROVED; the Storyboard Editor shows estimated vs requested minutes, word count, a warning when out of range, and a "Regenerate to fit length" button.
- ✔ 7 new tests (46 total pass): budget math, section stitching/renumbering, correction round with feedback, rejection of a model that never reaches the budget, mock path unchanged, length-check rules, regenerate endpoint gate.
- ✘ **Not tested against a real LLM** (no API key here): whether Claude/Ollama actually hit the budgets in one or two corrections is unproven. The fake LLM in tests only simulates short/long answers. Quality of long-form narration (repetition between sections) is also unproven.
- ✘ Pipeline `run_assets` still accepts hand-edited storyboards of any length; the length is caught at QC (after TTS+render), not before. Pre-render rejection would save time.

## 2. Did the 8-minute target pass?
**Duration: yes** (7.46 min, inside +-20 %). **Content quality: no, not publishable.** Reading the lesson 54 narration: the same `javascript:alert('XSS')` example is reused 6+ times, reflected-vs-stored is explained in 6 scenes, the quiz question appears 3 times (once with the answer before the question), a `javascript:` URI is presented as the search-box payload, scene 3 mixes up stored/reflected, a payload is mangled (`<scriptalert('XSS')</script`), and narration contains HTML entities (`&lt;script&gt;`) that the TTS would read as symbols. The gates added afterwards (shared-phrase repetition, speakability) flag lesson 54 (11 repetition findings + 6 markup findings), i.e. it would now be **rejected before TTS**. A full regeneration with those gates was NOT run; do not assume the 7B model passes them on the first try. This is a 7B-model ceiling (see recommendations).

## 3. Duration validation implemented (all tested)
1. Pre-generation: `validate_request` (5-25 min; schema, UI and generation all enforce it).
2. Per-section word budgets (10 sections: hook_intro, objectives, fundamentals, technical, demo, attack_scenarios, defense, mistakes, quiz, conclusion). JSON answer -> max 2 re-asks that include the model's own answer and a scene-count target -> per-scene plain-prose expansion/trim (small models write far better prose outside JSON) -> best attempt kept, section fails if >45 % (or >15 words) off.
3. Pre-TTS `preflight`: placeholder text, empty narration, repetition, unspeakable markup, undrawable diagrams, estimated length. Script depth check before storyboard (>= 40 % of target words).
4. Post-TTS: **measured** Piper audio vs the request (`audio_check`), before rendering.
5. Post-render: **ffprobe of the MP4** vs request and vs narration length (`video_check`, QC `video_duration_vs_narration`).
- WPS is no longer a constant: pooled from every measured sample in `storage/manifests/voice_calibration.json` and updated after each TTS run. Measured speed varies by text (1.9-2.8 w/s; code-heavy prose is slow): one calibration lesson gave 2.79, the XSS lesson 2.33; pooled 2.47. SCENE_OVERHEAD = 0.12 is conservative (actual render/audio was 1.07-1.13).
- Section files are saved as sections complete and a crashed run resumes with only the missing sections (cache key includes script, budgets, WPS).
- Hard limit raised to 25 min (was 12). Only the 8-minute path was run for real; 5, 12, 15, 25 are covered by unit tests of the windows/budgets only.

## Diagnosis of the first run (script v1, 14 blocking findings)
Root causes, each confirmed in the stored rows: (1) sources were 4 loosely related arXiv papers plus a model-guessed scikit-learn URL that returned 404, so ordinary ML statements had no evidence; (2) the reviewer reported "no source mentions this" as `technical_correctness` / high; (3) the same text appeared twice at different severities (dedupe key included severity); (4) the reviewer echoed claim-table entries and quiz distractors as findings, several with quotes that are not in the script; (5) `remediation` = critical is a security rule and made ordinary ML best practice a blocker; (6) one genuine issue: the definition never explained data/features/labels/training/inference. Script v2 (human-applied correction of finding 7) also contained a broken sentence (". and that"), caused by `apply_correction` ending a clause early.

## Changes
- Research: curated, live-verified beginner sources (Google ML Crash Course, IBM, Microsoft Learn, scikit-learn docs, NIST AI RMF), matched by keyword on title, summary and script prose with word boundaries. Search-API and model-suggested URLs are kept only if the page really loaded; arXiv search is a fallback only when no curated page matches. Hosts added to the allow-list: developers.google.com, www.ibm.com (plus other docs sites). SSRF, redirect, robots, timeout and size controls untouched.
- Claims: questions, analogies, transitions and fragments are not claims; semantically duplicate claims merge and keep every script section (`technical_claims.locations`, migration 0004); the correct answer of each quiz question is a claim, distractors and "Both A and B"-style answers never are; `critical` for remediation applies only in security domains.
- Reviewer (server-side, deterministic): findings whose quote is not in the script are dropped; "technically wrong" findings need a real quote from a retrieved source, otherwise they become `unsupported_claim` (capped at medium, non-blocking); findings that only repeat a tracked claim, quiz distractors (unless "also correct") and duplicates are removed. New categories `missing_citation`, `needs_qualification`. Counts of what was dropped are stored in the run summary (`refined`). Critical unsupported claims still block through the claims gate.
- Lesson quality: the `ai_ml` domain now lists what an introductory lesson must cover; it is given to the script writer and to the teaching reviewer.

# Phase 5: gate calibration, and why lesson 69 never reached TTS (2026-10-31)
## Blocking policy (server-side, `techreview.decide_blocking`; the model's own `blocks_approval` is ignored)
- wrong / unsafe / outdated / bad-demonstration findings (`technical_correctness`, `security_accuracy`, `demonstration_quality`, `outdated_information`): critical, high and medium block.
- `teaching_quality` blocks only with a concrete defect: the finding names one of the script's own learning objectives, says why the text fails it and gives a correction, and either (medium) the objective's key terms are demonstrably missing from the script or (high/critical) it is not just "vague / needs more detail" about a concept the script already contains. Low and info never block.
- `unsupported_claim`, `missing_citation`, `needs_qualification`: advisory, except high/critical in security domains. Critical unsupported claims still block through the claims gate.
- Gate checks for sections, references, length, narration and storyboard are unchanged. Findings and claims of a rerun supersede the older open ones; nothing is deleted (older findings become `superseded`, replaced claims are copied into the older run's summary).
- Migration 0005 adds `review_findings.objective` and `policy_note`.

## What was verified
- Tests: 237 passing (13 new for the policy, 1 for the lock behaviour below, 2 for the delete guard).
- Lesson 69 v3's 10 blocking findings, read against the script: all quotes exist; all 10 were "vague / too broad" comments, none named an objective, and for #21, #24-#29 the concept they asked for is already in the script (data, features, labels, hand-coded rules, train/evaluate/predict, three application examples, diverse datasets). #30-#32 were style comments. Under the new policy none of them would block.
- The review rerun under the new policy on v3 completed (1104 s) but its results were never inspected: the lesson was deleted by the user right after (see below). No claim is made about its findings.
- NOT done: script approval, TTS, rendering. Lesson 69 produced no audio and no video. No MP4 exists.

## Bug found: a slow review froze the dashboard
`run_review` held one database transaction (and row locks on claims and findings) for the whole review, 15-18 minutes on a local 14B model. Every click on the lesson (accept/reject a finding, "Run next", delete) queued behind it; on 2026-10-31 about 10 minutes of the user's clicks were stuck, which looked like "nothing is generating". Fixed: the model calls (`claims.judge_claims`, `techreview.review_script`) now run with no open transaction; results are written in one short transaction at the end (`claims.store_claims`). A regression test fails against the old behaviour (verified by putting it back).
The same lesson was also shown a 409 on delete because `RESEARCHING` is both a working status and the idle status after a rejected script; the delete guard now looks at whether a stage is actually running (newest stage log is `started`, less than an hour old).

- Human approval, TTS and render for a real lesson are still unvalidated end to end in this phase.
